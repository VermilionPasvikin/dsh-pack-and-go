## ADR-0001 · 平台支持矩阵与迁移方向（2026-11-10，Accepted）

**背景**：需求方要求“所有平台上的 DSH 之间”迁移。DSH Host 可运行在 Windows / macOS / Linux，插件运行在 Host 侧，数据在 Host 文件系统上。

**选项**
- A. 只支持三大桌面平台；
- B. 三平台为一级，WSL2 / Termux 为二级（尽力支持 + 限制说明）；
- C. 追加更多平台并逐一验证。

**决定**：B。一级：Windows 10/11（x64/arm64）、macOS 12+（Intel/Apple Silicon）、Linux x64/arm64；二级：WSL2、Termux/Android。迁移方向双向：Windows↔POSIX、macOS↔Linux、同平台不同安装形态。

**后果**
- 平台差异必须显式建模：路径、文件名合法性、大小写、权限位、符号链接、路径长度；
- 二级平台的问题以“限制说明 + 转换报告”处理，不作为首发阻塞；
- 无本地 `DSH_HOME` 的纯远端托管不在支持范围。

**关联**：SPEC §4、§FR-9。

## ADR-0002 · 选择模型：工作区 → 对话树（2026-11-10，Accepted）

**背景**：早期设计用“四种模式卡片”（仅对话 / 多对话 / 对话+工作区 / 仅工作区）作为第一步。需求方提出改为更贴合 DSH 原生的多级目录选择。

**选项**
- A. 保留四模式卡片；
- B. 工作区（一级）→ 对话（二级）树 + 一个全局“含项目文件”开关；
- C. 模式卡片作为捷径 + 树。

**决定**：B。勾工作区默认全选其下未归档对话；未归入任何工作区的对话进虚拟分组；文件开关全局唯一；工作区行悬停提供「只带文件」。

**后果**
- 去掉一层抽象选择，避免“模式”与后续勾选不一致；
- 需要实现“部分选中”“仅文件”两种特殊状态；
- 四种范围能力保留，只是不再显式呈现为模式卡片。

**关联**：SPEC §FR-2、§FR-4、NFR-1.5。

## ADR-0003 · 符号链接与权限位（2026-11-10，Accepted）

**背景**：工作区跨平台打包必须决定 POSIX 符号链接与 exec 位如何表示和恢复。

**选项**
- A. 链接默认解引用；POSIX exec 位在 POSIX 目标保留、Windows 忽略；
- B. 链接默认跳过（更小、更安全）；
- C. 链接默认保留（Windows 目标可能失败）。

**决定**：A。

**后果**
- 解引用可能增大包体积，需在转换报告中记录；
- Windows 目标丢失 exec 位属预期行为，不告警；
- “跳过链接 / 保留链接”保留为高级选项，默认不暴露。

**关联**：SPEC §FR-9、NFR-1.5。

## ADR-0004 · CLI 入口（2026-11-10，Accepted，阶段待定）

**背景**：无 GUI 的 DSH（纯 CLI/TUI，或服务器环境）同样需要迁移能力；需求方确认“提供 CLI 入口”。

**选项**
- A. 第二阶段提供 `dsh mover export/import` 子命令；
- B. 只做 Web UI；
- C. 第一版 CLI + UI 双入口。

**决定**：提供 CLI 入口，与 UI 共用同一包格式与 core；实现阶段待定（推荐第二阶段，不阻塞 Web UI 首发）。

**后果**
- core 必须与入口解耦，不依赖 Cordis UI 或浏览器 API；
- 若第一阶段即做，会推迟 Web UI 首发，需在开工前确认排期。

**关联**：SPEC §13、`docs/INDEX.md` 未决项。

## ADR-0005 · 会话头 cwd 改写（2026-11-10，Accepted）

**背景**：会话 header 的 `cwd` 由宿主平台的 `node:path.isAbsolute` 校验；Windows 路径在 POSIX 上不是绝对路径，会话会被判为非法 header。DSH 已提交的 generation 不可改写。

**选项**
- A. 只改写 header 的 `cwd`（写新 generation 文件）；
- B. 同时改写事件中出现的旧路径（风险高）；
- C. 不改，要求目标平台保持相同路径。

**决定**：A。

**后果**
- 跨平台会话可以打开并正确归组；
- 历史消息中的旧路径文本保持原样（只影响显示，不影响继续对话）；
- 需要实现 zstd 帧级编辑，并在写回后自校验（解回校验 header 与行数）。

**关联**：SPEC §FR-8、§9 风险表。

## ADR-0006 · 导入冲突与默认值（2026-11-10，Accepted）

**背景**：导入需要一组默认策略，避免让 0 技术背景用户做选择题。

**决定**
- 会话同 id 默认“跳过”；覆盖需显式选择，且先备份到 `<DSH_HOME>/backups/mover/<时间戳>/`；
- 工作区同路径默认“合并”；
- 附件按会话事件引用复制，不复制无关对象；
- 工作区默认保留 `.git`，排除 `node_modules`、`.venv`、`__pycache__`、`dist`、`build` 等可再生目录；
- 包为单文件 `.dshpack`（zip 容器，可被普通解压工具打开）；
- Agent 工具接口作为可选项，不阻塞首发。

**后果**
- 导入默认零参数可完成；
- 覆盖路径必须实现备份与回滚；
- 排除规则必须在导出前可见（估算体积），但默认值不暴露为参数。

**关联**：SPEC §FR-9、§FR-10、§FR-13、NFR-1.5。

## ADR-0007 · 会话日志改写策略（2026-11-10，Accepted，用户拍板）

**背景**：跨平台导入必须改写会话 header 的 `cwd`；DSH 日志是**多帧 zstd**（实测真实文件 851 帧、解压 4.89 MB），而 Node 单次解码只返回首帧，必须自行扫描帧边界。

**选项**
- A. 只重写首帧：扫描帧边界 → 解首帧 → 改 `cwd` → 重压首帧 → 其余帧原字节拼接；
- B. 全量解压后整体重压缩；
- C. `sessionPersistence.open(id, 'read')` 读逻辑事件 + `create(header)`/`append(events)` 由官方后端重建。

**决定**（2026-11-10 用户确认）：**A 作为主路径**（同版本迁移，快且保真）；**C 作为跨版本兜底**（在 M2 用 Host 服务实现）；**B 不采用**。

**后果**
- 同版本（v4→v4）：core 纯 Node 完成首帧改写，不依赖 DSH 服务；其余帧字节级保真。
- 跨版本（如源 v3）：core 拒绝改写，由 Host 走 C（`open` 触发历史格式迁移 + `create`/`append`）。
- 需要实现帧扫描与首帧校验；T1.5/T1.6 按 A 实现。
- 新增任务 T2.12（跨版本导入走服务重建），列入 M2。

**关联**：SPEC §FR-8、§9；TASKS T1.5/T1.6/T2.12；DEVLOG 013/014。

## ADR-0008 · UI→Host 通信方式（2026-11-10，Accepted，用户拍板）

**背景**：`@Remote` 是 Typert 装饰器，Client 契约由构建生成；纯 JS 插件无法直接通过 `ctx.remote` 暴露方法。T2.11 原计划因此不成立。

**选项**
- A. 自定义 HTTP 路由（`WebResourceRoute`）+ Client `fetch`，支持流式进度与取消；
- B. session command（`ctx.commands.register`），复用已有的 `commands` Remote；UI 等待期间显示“转圈 + 阶段文案”；
- C. 引入 Typert TS 构建链，使用原生 `ctx.remote`。

**决定**：**B 变体**。用 `ctx.commands.register` 注册 `mover` 命令；UI 在等待期间显示不确定进度（转圈）与阶段文案，完成后显示文本结果。保留纯 JS，不引入构建链。

**后果**
- 不提供精确百分比（用户已明确接受）；命令参数为文本形式；
- 不引入 HTTP 路由的信任模型风险，也不改变工程结构；
- 若未来确需精确进度，可新增 ADR 升级为方案 A；
- SPEC NFR-3 的“进度条 + 阶段文字”由“不确定进度 + 阶段文案”满足。

**关联**：TASKS T2.11、T3.4/T3.5；DEVLOG 042/043。

## ADR-0009 · CLI 入口形态（2026-11-10，Accepted，用户拍板）

**背景**：ADR-0004 确认“提供 CLI 入口，阶段待定”；用户于 2026-11-10 确认启动 M6。无 GUI 的 DSH（服务器/终端）需要迁移能力。

**选项**
- A. 独立 bin `dsh-pack-and-go`（`package.json` `bin`），纯文件访问 `DSH_HOME`；
- B. 作为 `dsh` 子命令（需要侵入 dsh CLI 或 profile 注册）；
- C. 复用 Host 命令（需要 DSH 运行中，无法离线使用）。

**决定**：A。独立 `dsh-pack-and-go` bin：
- `dsh-pack-and-go export --home <DSH_HOME> --out <文件> [--sessions id...]`
- `dsh-pack-and-go import --home <DSH_HOME> --pack <文件> [--target <目录>]`
- 与 UI 共用 core 与 `.dshpack` 格式；导入后写会话/附件/工作区文件，并更新 `workspace.json`（写前备份）。

**后果**
- CLI 不依赖 DSH 进程，可用于服务器导出；
- 导入后需重启 DSH 才能看到新会话（无服务刷新）；
- 工作区登记通过直接更新 `workspace.json`，与运行中的 DSH 并发需用户避免同时操作。

**关联**：ADR-0004、TASKS M6、`src/cli/index.js`。

## ADR-0010 · 导入文件选择器：Exact Fetch 上传通道（2026-11-10，Rejected）

> **2026-11-10 用户决定取消**：不新增上传通道与临时目录，维持现有「目录选择 + 扫描」
> （`uiWorkspace.pickDirectory` + `mover find`）的导入方式。以下内容仅作备选记录，不再实施。

**背景**：DSH 无文件选择服务（Host 无 `directory-picker` 可查询服务；Client 只有
`uiWorkspace.pickDirectory`）。用户要求「在文件选择器里直接选 `.dshpack`」，否决“选目录 + 扫描”。

**方案**：使用官方 **Exact Fetch 路由** 注册上传端点（api-gateway 明确推荐此方式承载 RPC 信封之外的响应）：

```js
ctx.connection.fetch.register({
  path: '/api/mover/upload',
  methods: ['POST'],
  requestBody: 'streaming',
  fetch: (request) => uploadHandler(request),
})
```

- 该通道由 Connection 的共享 Fetch handler 服务，**复用 Host/Origin 检查与浏览器认证**
  （`ConnectionFetchHandler`："Fetch handler for trusted, authenticated requests"），无需复刻信任逻辑；
- 请求体流式写盘到 `<DSH_HOME>/tmp/mover-uploads/<uuid>.dshpack`（上限 2 GiB，仅接受 `.dshpack` 后缀）；
- 返回 `{ path }`；Client 用 `<input type="file" accept=".dshpack">` 选择后 `fetch` 上传，
  成功即把 `path` 填入导入框，删除上传按钮只在文件选择可用时显示；
- 导入成功/失败后删除上传的临时文件；启动时清理 24 小时前的残留。

**前提**：`ctx.get('connection')` 可用且 `fetch.register` 存在（Web profile 默认满足）；
缺失时隐藏「选择文件」按钮并保留文本输入。

**替代方案**：B 复用命令附件（`submittedAttachments` file receipt）——需要额外研究附件 upload
协议，未采用；C 保留目录扫描——用户已否决。

**风险与缓解**
- 上传文件占磁盘：上限 + 24h 清理；
- 路由暴露：仅经 Connection 认证的请求可达；路径随机 UUID；
- 大文件流式写盘，不整包进内存（与 T1.10 流式修复一致）。

**状态**：Rejected（2026-11-10，用户取消）。维持「目录选择 + 扫描」，不新增路由与临时目录。

## ADR-0011 · 操作入口改为 Exact Fetch 路由（2026-11-10，Accepted）

**背景（已确认的缺陷）**
- 当前 UI 通过 `ctx.commands.execute` 调用 `mover` 命令。DSH 的命令实现会在会话日志中追加
  `command/run` 与 `command/done` 两条事件（官方行为，不可关闭）→ **每次导出/导入都让会话文件增长**；
- 命令必须绑定一个 Agent/Session 上下文（`sessionId` 作为 agent id）→ **0 对话时无法操作**；
- 用户要求迁移操作与对话上下文解耦。

**方案**
新增一条 **Connection Exact Fetch 路由**（DSH 官方推荐的 RPC 信封之外入口）：

```
POST /api/mover/exec
Content-Type: application/json
body: { "action": "list" | "export" | "import" | "inspect" | "find" | "size", "args": { ... } }
200:  { "ok": true, "result": <执行结果> }
4xx:  { "ok": false, "error": { "code": "...", "message": "..." } }
```

**Host**
- 在 `apply` 中：`ctx.get('connection')?.fetch.register({ path: '/api/mover/exec', methods: ['POST'], requestBody: 'buffered', fetch })`；
- handler：解析 JSON → 白名单 action → 调用已抽出的 `listCatalog / exportAllSessions / importPack / inspectPack / findPacks / measureWorkspaces`（与命令共用）；
- 认证：由 Connection 的共享 Fetch handler 负责（Host/Origin 检查 + 浏览器凭据），路由不自行复制信任逻辑；
- 缺失 `connection`（非 Web 组合）时不注册路由，UI 回退到命令通道。

**Client**
- `runAction(action, args)` 改为 `fetch('/api/mover/exec', { method: 'POST', headers: { 'content-type': 'application/json' }, body: JSON.stringify({ action, args }) })`（同源自动携带 cookie）；
- 导出/导入/list/inspect/size/find 全部改走该通道；
- 命令通道（`/mover ...`）保留给聊天命令行与 CLI，UI 不再使用。

**为什么不是 ADR-0010**：ADR-0010 是**文件上传**通道（接收 `.dshpack` 字节、落临时目录），已被取消；
本 ADR 只增加一个**小型 JSON 操作入口**，不接收文件、不写临时目录。

**风险与缓解**
- 新增路由面：仅 POST + 白名单 action + 参数校验；认证复用 Connection；
- 破坏命令通道：保留命令并共享同一批函数，UI 切换后命令仍可用；
- 版本兼容：`connection.fetch.register` 不存在时回退命令通道（保留旧路径）。

**实施范围**：新增 `src/host/exec-route.js`；`host/index.js` 注册；`client/client.js` 的 `runCommand` → `runAction`；单测（action 分发、错误映射、回退）。

**验收**
1. 在**没有任何对话**的一次性 home 中可完成导出/导入；
2. 操作前后对比会话文件大小：不再增长；
3. 命令通道仍可手动使用。

**状态**：Accepted（用户批准），已实施：`POST /api/mover/exec`（DEVLOG 90/109/118）。

## ADR-0012 · 预检改为“默认执行、不可关闭”（2026-11-10，Accepted）

**背景**
- 当前「导出前预检」是可选勾选项；`preflightWorkspace` 检查的是**跨平台**风险（Windows 非法文件名、
  大小写冲突、路径过长、符号链接、权限位）。同平台导出（Windows→Windows）通常为 0 项 →
  用户观察到“勾了也永远 0 项”，选项显得无意义；
- 用户提议：**取消该选项，导出时默认做一次预检**。

**收益**
1. UI 更简（少一个参数，符合 NFR-1.5 “只暴露必要控制”）；
2. 用户不会因为忘记勾选而在导入端才发现跨平台问题；
3. 预检结果可并入导出完成页摘要（“0 项风险”/“N 项需转换”），信息更完整。

**风险与成本**
1. **每次导出多一次目录遍历**：`preflightWorkspace` 需要扫描文件名/属性（不读内容）。500 MiB
   工作区约 +1–2 s；GB 级工作区可能 +5–10 s（与打包本身同量级，可接受但需实测）；
2. **大目录/权限异常时的失败处理**：预检失败不应阻断导出（建议：记警告、继续导出）；
3. **“0 项”仍可能出现**：同平台导出没有转换需求，默认预检的结果仍是 0 项——只是不再需要用户勾选，
   文案需解释“0 项 = 当前平台无需转换”；
4. 与 T3.13 高级选项的一致性：移除该开关后，高级选项只剩全量/额外排除/包名等。

**建议**
- 采纳用户提议：**默认预检、无开关**；预检结果并入完成页（`预检 N 项` / `预检通过`），失败仅警告不阻断；
- 若实测大工作区预检耗时不可接受，回退为“后台异步预检 + 完成页提示”（不阻塞导出）。

**状态**：Accepted（2026-11-11 用户采纳）；实施：导出默认执行预检，导出页移除「导出前预检」开关。

## ADR-0013 · 导入模式：强制指定目录 + 冲突三选（2026-11-11，Accepted）

> **2026-11-11 用户拍板（Accepted）**：
> 1. 采纳「强制指定目录」：移除「放回原路径」；目标目录必填；
> 2. 会话冲突只暴露 **跳过 / 覆盖** 两个互斥选项（选 3c，不做重命名另存）；
> 3. 附件冲突跟随会话策略（附件捆绑在会话里，同一策略处理）；
> 4. 工作区冲突：用户在源目录时可能复用已有工作区（按路径判断，不重命名）；
> 5. 默认目标目录 `~/dsh-pack-and-go-import`；
> 6. **导入失败时不得自动回退到默认目录**，必须红字报错诚实提示失败。

**背景**：现有导入把「落点（原路径/指定目录）」与「冲突策略（跳过/另存为新对话）」并列。
用户反馈：
- 选择「另存为新对话」时指定目录实际失效（fork 保留源 cwd，会话落回原工作区）；
- 整个导入阶段的选项组合让人难以理解。

**用户提案（OS 复制文件风格，已确认）**：
1. 放弃「放回源路径」选项，导入时**强制指定目录**；
2. 冲突行为由用户选择：**跳过 / 覆盖**（互斥两选）。

## 可行性分析

### 1. 强制指定目录 —— 可行 ✅

- `pathMap` 始终由用户目录生成（`<目标目录>/<工作区标题>`），删除「原路径」分支；
- 原路径恢复场景仍可通过「目标目录手动选为原路径」实现，只是不再作为一键选项；
- 好处：消除跨平台路径校验、语义单一（导入 = 放到你指定的地方）；
- 代价：同机恢复原位多一步（选原路径）；用户选原路径时需定义「复用已有工作区」而非重命名。

### 2. 冲突「跳过 / 覆盖」—— 现有已可用 ✅

- 跳过：同 id 会话不写入；覆盖：直接写盘（覆盖前有备份）。

### 3. 冲突「重命名另存」—— **存在硬约束** ⚠️

用户期望像 OS 复制文件：`x.md` → `x (1).md`。分两层看：

| 对象 | 重命名另存是否可行 | 说明 |
|---|---|---|
| **工作区目录** | ✅ 可行 | 目标目录存在时改为 `<标题> (1)`、`<标题> (2)`；登记标题同步去重 |
| **会话** | ❌ 不可行（跨目录） | DSH 会话有 cwd 锚定；官方复制入口 `fork` **保留源 cwd**；改写 header id 会触发 `delivery marker` 校验失败（已实测） |

因此「会话重命名另存」只能退化为以下三种定义之一，需要用户选择：

- **3a. fork 复制（保留原工作区）**：复制出全新会话，但 cwd 不变 → 仍归原工作区（与「指定目录」矛盾，这正是本次问题的来源）；
- **3b. 只对工作区目录重命名**：会话冲突仍用跳过/覆盖，重命名仅作用于工作区文件目录（OS 风格目录级）；
- **3c. 不做重命名**：只保留跳过/覆盖（最简、无歧义）。

## 优劣势

| 方案 | 优点 | 缺点 |
|---|---|---|
| 强制目录 + 三选（含 3a/3b/3c） | 语义接近 OS 复制；选项少；跨平台一致 | 会话级重命名不可靠（3a 落回原工作区，3b 只是目录级） |
| 现状（落点 + 冲突） | 保留同机复制能力 | 无效组合、概念混乱（用户已否决） |
| ADR-0012 等旧提案 | 两步向导/智能默认 | 均未覆盖「重命名另存」诉求 |

## 建议

- 采纳「强制指定目录」+「跳过 / 覆盖」；
- 「重命名另存」按 **3b** 实现（目录级重命名），并在 UI 说明「对话冲突仍按跳过/覆盖处理」；
- 若坚持会话级重命名，则接受 3a 的 cwd 限制并在 UI 明确提示。

## 待用户拍板

1. 是否批准「强制指定目录 + 跳过/覆盖」？
2. 会话冲突的「重命名另存」选 3a / 3b / 3c？
3. 用户把目标目录选成源路径时：复用已有工作区（更新）还是强制重命名新目录？
4. 默认目标目录：`~/dsh-pack-and-go-import` / 记住上次目录？

**状态**：Accepted（2026-11-11，用户批准）。实施见 DEVLOG 111。

## ADR-0014 · 导入行为决策：迁移覆盖 + 边界规则（2026-11-11，Accepted）

**背景**：ADR-0013 确定「强制指定目录 + 跳过/覆盖」后，审查发现「新目录落点 + 同 id 冲突」等边界行为未定义。
用户审阅 `docs/IMPORT-BEHAVIOR-TREE.md` 后采纳以下规则（全部批准）。

**决策**

1. **迁移覆盖**：覆盖导入且目标 cwd ≠ 现有 cwd 时，备份并移除旧位置的同 id 会话目录，写入目标位置；结果必须提示
   「已迁移覆盖：<原工作区>/<会话> → <新工作区>/<会话>」。目标 cwd = 现有 cwd 时退化为原地恢复。
2. 旧格式包（sessionFormat < 4）：直接写文件，结果提示「旧格式，打开时自动迁移」。
3. 目标目录内已有同名目录（未登记为工作区，非本插件创建）：新建 `标题 (1)`，不复用用户目录。
4. 工作区文件同名冲突：覆盖写，结果统计「覆盖 N 个文件」。
5. 附件同名冲突：覆盖（内容寻址，同名即同内容）。
6. 覆盖但现有会话 cwd 未知：**拒绝覆盖**并红字提示（安全优先）。
7. 纯对话包（无 workspaceKey）：cwd 保留源路径，结果提示「N 个对话未归组」。
8. 目标目录 = 源路径：允许，视为原地恢复（复用工作区）。
9. 包内工作区无有效会话写入：**空工作区也登记并还原其文件**（用户可能先建工作区、后建对话）；结果标注「M 个暂无对话」。
   （2026-11-11 修订：原为「不登记、不还原」，因“先建工作区后建对话”场景与目录复用问题被用户否决；见 DEVLOG 120。）
10. fork 链父子：父会话被跳过时，子会话强制跳过（保持链完整），结果提示。

**后果**：导入结果文本需承载迁移覆盖/覆盖文件/未归组/空工作区等细节；`importSessionsToDisk` 增加旧目录移除与备份；
`planImport` 增加迁移覆盖与父子联动；附件恢复按「实际写入会话引用的附件」过滤。

**状态**：Accepted，实施见后续 DEVLOG。

## ADR-0015 · 导出支持「仅工作区」模式（2026-11-11，Accepted）

**背景**：导出以会话为入口，工作区文件只能随会话导出；无法只导出工作区，也无法导出「有文件无对话」或「完全空文件夹」的工作区（SPEC v1.0 范围包含「仅工作区」）。

**决策（用户拍板，B+C）**：

1. 先做 Host/CLI 管线，再做导出页「仅工作区」模式入口；
2. 包格式：`mode: 'workspaces'`、`sessions: []`、`workspaces` 非空；**不要求向后兼容**（插件尚未发布）；
3. 工作区导出**包含文件内容与目录结构**；空文件夹工作区保留目录骨架（`fileCount: 0`），导入时 `mkdir` + 登记；
4. CLI：`export --workspace <path>`（可多次，至少一个）；exec：`export.workspaces`；
5. 导入端复用「空工作区也登记」（ADR-0014 决策 9 的 E 版），无需新逻辑。

**后果**：导出决策树新增模式分支；新增 `exportWorkspacesOnly`；导出页新增模式切换；SPEC 升 v1.2。

**状态**：Accepted，实施见 DEVLOG 124。

**关联**：TASKS T3.5；ADR-0008。

## ADR-0016 · 全权限位保真（POSIX mode 恢复）（2026-11-12，Proposed）

**背景**

- devlog 134 修复后，导入端只对「带 exec 位」的文件 `chmod`；其余文件与目录按创建时的默认 mode 落盘（文件 `0666 & ~umask`、目录 `0777 & ~umask`）。
- 实测（Linux，本机 umask=`002`）：包内 `normal.txt` 为 `0o100644` → 导入后 `0o664`；目录 `subdir` 为 `0o40775` → 导入后 `0o775`。
- 包格式本身没问题：zip 的 external attributes 已逐条记录 mode（如 `0o100755`），`readZip` 也能读回；**丢失发生在恢复端策略**，不是格式缺陷。
- 影响：
  - 安全面：`0600` 私钥/凭据类文件导入后可能变成 group 可读写（`0664`）；`0700` 目录变 `0775`。
  - 可用性面：`0444` 只读文件被覆盖为可写；`0755` 脚本已由 devlog 134 修复。
- 现有规格只覆盖 exec 位：SPEC FR-9「有 exec 位的文件在 POSIX 目标恢复 `755`」；ADR-0003「POSIX exec 位在 POSIX 目标保留、Windows 忽略」。**全权限位保真属于超出既有规格的新决策**，故立此 ADR。

**范围定义**（避免歧义）：本 ADR 的「全权限位」= 每条目的 `mode & 0o777`（owner/group/other 的 rwx），**不含** setuid/setgid/sticky。

**选项**

| 选项 | 做法 | 收益 | 成本/风险 |
|---|---|---|---|
| A. 维持现状 | 只恢复 exec 位 | 零改动；与 SPEC 字面一致 | 权限漂移继续；`0600`→`0664`、目录放宽；用户需手工 chmod |
| **B. 全量保真（推荐）** | POSIX 目标且源平台为 POSIX 时，文件与目录恢复 `mode & 0o777`；Windows 目标忽略并记录；win32 源包跳过该逻辑 | 往返保真；消除安全漂移；旧包零回归 | 需处理目录两阶段 chmod、setuid 剥离、失败告警；多约 30 行 + 测试 |
| C. 全量保真（不区分源平台） | 同 B，但 win32 源包也按 mode 恢复 | 实现更简单（无源平台分支） | Windows 导出的 mode 是合成值 `0644`，会把目标已有 `0600` 文件**放宽**；跨平台语义倒退 |
| D. 仅报告不恢复 | 统计「N 个文件权限位将变化」写进结果/报告 | 零风险；用户可自行处理 | 不解决保真；每台机器都要人工补救，违背「换台电脑继续」目标 |

**决定（提案，待用户批准）**：**B**，并受以下硬约束：

1. **仅 POSIX 目标**生效；Windows 目标保持现状（忽略并记录，与 ADR-0003 一致）。
2. 只取低 9 位；**显式剥离 setuid/setgid/sticky**（`mode & 0o777`），杜绝「导入一个包就拿到提权位」。
3. **源平台为 `win32` 的包跳过全量恢复**：其 mode 是导出端合成值（默认 `0o100644`），按它恢复会把目标端更严格的权限放宽。
4. **目录两阶段**：先按可写创建目录 → 写完全部文件 → 最后统一 `chmod` 目录；否则包内 `0500`/`0555` 目录会导致后续写入失败。
5. 缺失或为 `0` 的 mode：跳过，不 chmod。
6. `chmod` 失败（`EPERM`、只读挂载、网络文件系统）：记 warning、不阻断导入（与附件策略一致）。
7. 结果与转换报告：统计「恢复权限 N 个文件 / M 个目录，失败 K 个」，`restoreWorkspaceFiles` 返回值新增 `modes: { applied, failed }`；**不新增包格式字段**。
8. 覆盖已有文件时权限一并改写：与「覆盖」语义一致，结果中按 `overwritten` 现有计数提示。

**后果**

- 包格式与 `schemaVersion` 不变，无迁移；`readZip` 已提供 mode，无需改动 zip 层。
- Windows 源包行为与今天完全一致 → **零回归**；POSIX 往返变为保真。
- 新增测试：`0644` 保持、`0600` 保持、`0755` 保持、目录 `0700` 保持、setuid 位被剥离、Windows 目标行为不变、win32 源包跳过、umask 不影响结果。
- 性能：每条目一次 `chmod`；1 万文件量级预计 +20–50 ms（未实测，实施时补测并记 DEVLOG）。
- 回滚：纯恢复端行为，revert 对应提交即回到 ADR-0003 状态。
- 已知风险：FAT/exFAT/部分网络文件系统 chmod 语义缺失 → 只会有 warning；在只读父目录下收紧目录权限会失败 → warning。

**待用户拍板的点**

1. 是否接受方案 B（而非 A/C/D）；
2. 是否接受「win32 源包跳过」这一分支；
3. 是否需要开关（默认开启的 `--preserve-modes` / UI 选项）——若需要，本 ADR 需追加参数与 UI 暴露成本。

**关联**：SPEC §FR-9、ADR-0003、DEVLOG 134、TEST-CASES P-05a、`src/core/workspaces.js`。

**状态**：Proposed（2026-11-12，待用户批准；批准后改为 Accepted 并实现）。
